**1. P1 — Staff onboarding can activate an attacker’s pre-registered credentials**

Location: [team API:71](/Users/skycastle3/Desktop/gary_group/gary_home_website/app/api/admin/team/route.ts:71), with assignment at line 76 and optional password replacement at line 80. The [account lookup:18](/Users/skycastle3/Desktop/gary_group/gary_home_website/supabase/migrations/20261025055215_direct_staff_accounts_profiles_and_notifications.sql:18) accepts unconfirmed Auth accounts.

An attacker can sign up using a future staff member’s email and an attacker-known password without proving mailbox ownership. If an authorized administrator later selects “Assign and keep existing password,” the API confirms that email and assigns the requested staff role while retaining the attacker’s password. This attack depends on the administrator assigning that particular email; it does not let an anonymous caller invoke the staff endpoint directly.

The replacement option has a related failure path: membership is granted before password replacement, so a failed replacement leaves the old credentials active with staff access.

**Evidence:** the current API route, run with a mocked Auth boundary, returned HTTP 200 with confirmation and assignment performed and the old password preserved. A replacement failure returned HTTP 409 after confirmation and assignment, retaining the old password. The complete current schema in PGlite independently accepted the unconfirmed-account lookup and subsequent assignment; the password sentinel remained unchanged and `private.is_editor()` became true. No live Auth login was attempted. [Supabase documents direct administrative confirmation and password updates](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid).

**Fix:** preserve credentials only for accounts whose mailbox ownership was already verified. For an unconfirmed account, require mailbox verification or establish trusted replacement credentials before confirmation and membership assignment. Failed replacement must leave no usable staff grant.

**2. P2 — Email changes prevent normal staff-access revocation**

Location: [set_staff_access:31](/Users/skycastle3/Desktop/gary_group/gary_home_website/supabase/migrations/20261025055215_direct_staff_accounts_profiles_and_notifications.sql:31).

Disabling a membership resolves its stored email against the current Auth email, even when `enabled=false`. After a confirmed email change, the lookup fails and the owner cannot disable that membership through the normal control.

**Evidence:** owner revocation failed with SQLSTATE `23514`, leaving `active=true`. Restoring the old Auth email restored editor access without reassignment. While the emails differ, the current access helper correctly denies access; the defect is the inability to revoke the surviving grant.

**Fix:** authorize disabling by target membership UUID and the acting user’s hierarchy. Require current verified-email/domain eligibility when assigning or restoring access.

**3. P2 — Administrative account and property deletion fails when enquiries reference them**

Location: [enquiry update guard:111](/Users/skycastle3/Desktop/gary_group/gary_home_website/supabase/migrations/20261021201948_customer_portal.sql:111).

Deleting a referenced Auth user or property invokes an `ON DELETE SET NULL` update on enquiries. Without an end-user `auth.uid()`, the cancellation-only trigger rejects that referential update, even for trusted administrative operations.

**Evidence:** both administrative Auth-user deletion and property deletion failed with SQLSTATE `42501`: `Customers may only cancel their own active viewing requests.` Authenticated staff deletion through the application is a different path and can work.

**Fix:** support trusted referential maintenance while retaining the restrictions on customer changes to ownership, appointment, status, replies, and private fields. Test both parent-deletion cases without an end-user identity.

**4. P2 — Direct database inserts bypass public-form abuse controls**

Locations: [enquiry INSERT grant:120](/Users/skycastle3/Desktop/gary_group/gary_home_website/supabase/migrations/20261021152453_gary_home_cms.sql:120), [feedback grant:31](/Users/skycastle3/Desktop/gary_group/gary_home_website/supabase/migrations/20261023134954_feedback_and_assistance_reports.sql:31), and [assistance grant:105](/Users/skycastle3/Desktop/gary_group/gary_home_website/supabase/migrations/20261023134954_feedback_and_assistance_reports.sql:105).

Anyone with the public project URL/key can insert directly through the Data API. Those inserts never execute the application endpoints’ origin, honeypot, or rate checks. The row policies constrain fields and protect private reads, but do not enforce equivalent abuse controls.

**Evidence:** the complete schema accepted 20 anonymous enquiries, 20 feedback submissions, and 20 assistance reports in isolated Postgres, with each count checked afterward.

**Fix:** enforce validation and durable abuse controls on every accepted submission path. Strengthening only the website route leaves the direct insert path available.

**5. P2 — Direct assistance-review writes bypass staff-attribution hierarchy**

Location: [assistance review policies:117](/Users/skycastle3/Desktop/gary_group/gary_home_website/supabase/migrations/20261023134954_feedback_and_assistance_reports.sql:117). The intended additional restriction is in the [later review RPC:86](/Users/skycastle3/Desktop/gary_group/gary_home_website/supabase/migrations/20261026064456_staff_peer_and_lower_role_visibility.sql:86).

The RPC rejects a manager’s new commission attribution to a higher-role owner. However, the manager can directly insert or update `assistance_reviews`, whose policies check management status and reviewer identity without validating the credited account’s eligibility.

**Evidence:** the RPC rejected a new manager-to-owner attribution with `23514`; a direct insert of that same attribution succeeded and persisted the owner UUID. This alters attribution records, not the owner’s access role.

**Fix:** enforce credited-account eligibility on table writes, or make a guarded entrypoint the only write path. Preserve the intentional ability to retain an existing higher-role attribution.

**6. P2 — A delayed favourites import reverses a newer removal**

Location: [importSaved:441](/Users/skycastle3/Desktop/gary_group/gary_home_website/components/site-context.tsx:441), especially the unconditional union at line 445.

Import captures browser favourites, awaits the database write, then merges every captured ID into the displayed saved list. It does not coordinate those IDs with later remove operations.

**Evidence:** using the real React provider, browser favourites were `[A,B]` and the signed-in database contained `[A]`. While importing B was delayed, removing A completed. Resolving the import restored A in the UI even though its database row remained deleted.

**Fix:** coordinate mutations per property, or reconcile authoritative results after pending mutations settle so the newer removal wins.

**7. P2 — CRM drafts disappear after same-account reauthentication**

Locations: [Studio auth gate:167](/Users/skycastle3/Desktop/gary_group/gary_home_website/components/admin-page.tsx:167) and [CRM local draft state:15](/Users/skycastle3/Desktop/gary_group/gary_home_website/components/customer-manager.tsx:15).

When the session becomes null, Studio unmounts CustomerManager. Its unsaved contact/notes state lives inside that component, so signing back into the same account recreates an empty form. Property/settings drafts already use lifted state and do not have this particular failure.

**Evidence:** enter a new CRM customer name, lose the session, then restore the same owner identity. The real component loses the editing form and entered name.

**Fix:** keep CRM drafts in account-scoped state above the authentication gate. Clear them on explicit sign-out or account change, and preserve them across same-account reauthentication.

**8. P2 — Customers Refresh does not load new enquiry-only contacts**

The directory combines profiles, CRM records, and shared enquiries, but its Refresh button reloads only the first two sources. Newly arrived guest enquiries therefore do not appear as contacts or history after that refresh.

**Evidence:** with the real components, a new guest stayed absent after Customers Refresh; a full Studio refresh immediately revealed the guest.

**9. P2 — Unpaginated reads silently omit records beyond the Data API row cap**

Locations: [public content:26](/Users/skycastle3/Desktop/gary_group/gary_home_website/lib/public-content.ts:26) and [CRM reads:29](/Users/skycastle3/Desktop/gary_group/gary_home_website/components/customer-manager.tsx:29).

These lists issue one query and then search/filter the returned subset in memory. Public detail routes also search that same returned catalogue, so a published property beyond the cap can receive a false 404 and disappear from the sitemap. Supabase’s [documented default is 1,000 rows, configurable per project](https://supabase.com/docs/reference/javascript/v1/select); the live project’s cap was not inspected.

**Evidence:** the real SDK/public loader against a simulated 1,000-row response cap returned 1,000 of 1,001 stored homes, made exactly one properties request, sent no range, and silently omitted the final slug.

**Fix:** use deterministic pagination and database-side filters/counts. Fetch detail records by slug directly and exhaust relevant pages for sitemap generation.
