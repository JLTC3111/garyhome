# Editable listing IDs

Staff can edit the displayed listing ID on new and existing listings. A new listing can leave it blank for automatic assignment; an existing listing requires an ID. Short numbers and pasted `GH` codes normalize to at least two digits: `5`, `GH-5` and `GH-000005` become `GH-05`. Numbers grow naturally past 99 (`GH-100`) and custom IDs accept up to twelve digits. The internal UUID and property URL stay unchanged, preserving links, favourites and related records. Historical enquiry snapshots retain the code recorded at that time. Search accepts both the current short code and previously used padded codes.

The field checks the local catalogue immediately and checks current database records after a short pause when a code changes. Availability is advisory until Save. The existing unique constraint reserves codes across published, draft and archived listings. A conflict at save time keeps the editor open and explains that another ID is required. Regular customers do not gain listing write access.

Migration `20261030075152_editable_listing_ids.sql` introduced an invoker trigger in the private schema. Code assignments take a transaction-scoped advisory lock. Automatic IDs continue from the existing sequence and skip custom codes already reserved. Custom assignments and automatic assignment use the same lock, with the unique index as the final concurrency check. Untrusted roles must have current staff access before allocating an ID.

Migration `20261102065952_short_listing_ids.sql` shortens existing codes and changes future assignments to the same two-digit minimum. It locks catalogue writes during the conversion, checks for duplicate numeric identities before changing rows, and preserves the sequence and every numeric identity. It also updates the built-in portal help example. Fresh setup includes the migration; the browser catalogue uses the same short codes.

Every update receives a monotonically advancing timestamp from the database. The Studio submits the timestamp it originally read as a condition on the update. If another editor has saved first, the stale save affects zero rows, refreshes the catalogue's saved version, and leaves the unsaved draft open. The message explains how to copy edits before closing and reopening the listing to review the saved version. Writes are not automatically replayed or silently merged. A slow save also advances the timestamp of newer edits in the same open form, so those edits can be saved normally afterward.

Local PostgreSQL tests cover the upgrade of existing listings, retention of UUIDs, favourites and enquiry snapshots, automatic allocation past 99, longer IDs, equivalent padded-input conflicts, VND validation, all-status uniqueness, timestamp ownership, public reads and staff-only writes. Studio tests cover ID normalization, save conflicts and duplicate checks.

Applied to project `duyiihsmaqfgwezmsnjs` on 2 November 2026; all 18 live listings have unique short IDs. Frontend changes are local and have not been deployed.
