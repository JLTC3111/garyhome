# Gary Home property photo rename

## Reference model

The public `property-media` bucket contains listing uploads. `properties.images` stores URLs in display order, with the cover first. `image_filenames` and `image_metadata` use those URLs as keys. The public listing query, gallery, thumbnails, staff preview, and cover consumers read this ordered list. The November 19 read-only inventory found 667 listing references to the bucket and one Home hero reference. It found no saved transformation or query URLs among the listing references.

The migration rewrites every matching listing photo and map key, plus the known Home hero, neighbourhood, author, activity, editorial image and source links. It preserves positions, public filename approval, EN/VI descriptions and alt text, and saved derivative query options. The operation blocks on an ambiguous Storage origin or incompatible metadata alias. A copied object retains the original bytes and embedded watermarks. Supabase Copy preserves file metadata and uses insert-only behavior by default. [Supabase Copy Objects](https://supabase.com/docs/guides/storage/management/copy-move-objects) · [Storage copy implementation](https://github.com/supabase/storage/blob/master/src/http/routes/object/copyObject.ts)

Existing photos renamed by the Home Owner move to `properties/renamed/<listing ID>/<normalized basename>`. The editor displays the current Storage filename and labels the original upload name separately. The existing public filename preference applies to the original upload name.

## Deploy and verify

1. Confirm the filename and image metadata columns and the objects from the [baseline rename migration](../supabase/migrations/20261119054408_property_photo_storage_rename.sql) are present. The November 19 production check found the baseline objects without a matching migration-history entry. Reconcile that history before using an automated migration tool.
2. After review, apply any missing prerequisites and then the Owner-only authorization migration before deploying the route and editor. A current Home Owner can choose **Rename and remove old copy** after reviewing the preview and link warning. Earlier reservations keep their retention behavior, including on retry. [Rename completion migration](../supabase/migrations/20261119073707_property_photo_rename_completion.sql) · [Owner-only migration](../supabase/migrations/20261119183631_property_photo_rename_owner_only.sql)
3. In an approved test environment, start with an isolated photo that has a duplicated extension. Confirm the Owner can rename and Admins, Managers, and Editors cannot use the controls or RPCs. Test a collision and verify that a successful rename preserves the cover position. Reopen the listing and reload the public page. Check the gallery, thumbnails and cover, captions and alt text in each locale, and the original-filename preference. Check rename history for confirmed removal or pending cleanup.

## Retention and rollback

- A reservation precedes the Storage copy. The server compares the source and destination SHA-256 digests and MIME type before an atomic reference update. A timeout or stale edit leaves the job in history. Reopen the listing and retry with the same name. If a staged destination has unexpected bytes, quiesce the route, confirm the job is unapplied and the destination is unreferenced, then use the Storage API for any separately approved staged-file removal. Preserve the reservation for retry.
- The server reads the saved listing before attempting cleanup. It checks known saved Home references, verifies the current replacement, and confirms the old object's absence after using the Storage API. If cleanup remains pending, the new listing image is already saved and the Owner can retry from **Rename history and old copies**. Historical copies require a separate reviewed removal. Old links in emails, bookmarks, exports, and external pages may fail once the object is removed. Cached copies can survive for the CDN cache lifetime. [Supabase CDN caching](https://supabase.com/docs/guides/storage/cdn/smart-cdn)
- To reverse a committed rename, pause the rename and cleanup route. Verify the digest and restore the original to its exact old key via the Storage API with collision protection if needed. Reconcile the registry and reverse the still-current references in one separately reviewed transaction, preserving edits since the rename. Keep the replacement until the restored listing is checked. The audit row identifies the keys, original listing, affected versions, actors, and removal state.

Fixture verification uses an isolated database, simulated Storage, and nonvisual editor and gallery tests. Hosted rename and browser reload behavior still require an approved environment for verification.
